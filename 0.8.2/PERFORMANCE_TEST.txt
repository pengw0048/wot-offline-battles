WORLD OF TANKS 0.8.2 BOT PERFORMANCE TEST
==========================================

Purpose
-------

This temporary diagnostic build samples one render frame in four and writes
one aggregate PERF line to python.log every five seconds. It does not require
any server changes or debug mode.

Install
-------

1. Close the game.
2. Delete the existing res_mods/0.8.2 directory.
3. Copy the supplied 0.8.2 directory into res_mods.
4. Start the LAN server normally, then start the client.

Test
----

Play one battle for at least 30 seconds after all bots appear. A useful sample
contains both the countdown and at least 20 seconds of normal movement.

If two clients are available, collect python.log from both machines. The PERF
line identifies the client as role=authority or role=replica. This comparison
separates local bot simulation cost from rendering and network interpolation.

Send the complete python.log, or only lines containing:

    [OFFHANGAR] [NOTE] PERF
    [OFFHANGAR] [NOTE] LAN NET

                  be near zero because retail physics owns native/native pairs.

Refresh/deferred counters show how many order, navigation, driver, and tree
jobs actually ran versus reused or deferred work. They are call counts, not
milliseconds. Movement integration and canonical pose commits are continuous
for every locally simulated live bot and are never part of those budgets.

Expected result for protocol 8
------------------------------

On an authority client with a healthy server-navigation stream, nav_server
should be close to the number of active moving bots while nav_tick/nav_target
are absent or near zero. The release target is at least 30 FPS after the lineup
is loaded. This must be accepted from a real Windows 0.8.2 client; the local
server benchmark verifies path throughput but cannot prove native BigWorld
render, collision or model cost.

The server terminal must also report `BOT NAV active=True`, `failed=0`, and a
maximum search budget near 6 ms or lower. A short non-zero `pending` count
during the opening second is expected; an `oldest` value that keeps growing is
not.

Build 1.8.59 prints one `SERVER PERF` line every five seconds during a
battle. `cpu_core` is process CPU as a percentage of one core; `avg`, `p95`
and `max` are complete server-tick times. `stage` separates movement, planning,
navigation, snapshots, diagnostics and dispatch, while `wire` separates JSON
encoding from socket writes. A healthy 30 Hz server remains well below the
33.3 ms tick budget with `overruns=0`; that rules out the simulation tick
itself, but `snapshot`, `outbound` and `sent` must still be checked for TCP
head-of-line delay.

Each accepted TCP connection also prints its actual send buffer and the
requested 131072-byte bound. This makes accidental reintroduction of a large
kernel backlog visible without relying on the HUD's 999 ms display clamp.
`snapshot=base:<B>,orders:<B>,attach:<n>/<total>` separates the normal snapshot
body from attached bot orders. `outbound` adds the current in-flight count, its
maximum age and the longest completed send in the five-second window. `sent=`
reports messages and KiB that actually completed sendall by type; the older
`messages/data` values are offered/encoded work and can include snapshots later
coalesced away. Growing age or send_max alongside high RTT identifies a blocked
TCP writer even when the application queue is already empty.

LAN NET separates transport and scheduling stalls. max_socket_gap is a real
receive pause; max_queue_age means the packet arrived but the game thread was
late applying it. snapshots is the server stream rate, and bot_updates is the
authority's actual new-pose rate. poll is average main-thread LAN callback
time; snapshot_apply is the average newest-snapshot application time.
Authority clients reuse unchanged server-navigation coordinate conversions
and no-op health updates; handoff and replica snapshots deliberately retain
the complete application path.

Times are milliseconds per sampled frame. The value after '/' is the average
call count per sampled frame. Some stages are intentionally nested: driver
includes direction, and physics includes terrain and collision work. Do not
add the stage times together; use callback as the total.
